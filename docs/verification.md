# Verification

Each trust boundary in Pigeon, where it reads or checks something it can't take on faith, with what checks it today and what isn't checked yet.

A trust boundary is code that decides whether to accept bytes from someone else: a signature, a log entry, an envelope, a frame, a file. The checks below are what would go red if one of those decisions were weakened. "Own tests" means unit tests written alongside the code; "vectors" means expected answers taken from a published source; "property" means fast-check tests over generated inputs.

## How this map is kept

- A change that adds a trust boundary (a signed format, a log, a parser) adds a row here, with "not yet verified" in its last column until something independent checks it.
- A change may not delete or loosen an existing check (a vector, a rule, a property) without saying why in its pull request.
- When a check lands, its row says what it is, and the "not checked yet" cell shrinks.

Everything here runs in `mise run check`, except the end-to-end tests, which run with `mise run e2e`.

## What this can't show

The checks show the code does what the docs say. They don't show the docs are enough: that is what a formal model of the protocol and an outside review are for, and Pigeon has neither. A property or bounded check covers what it generates and nothing past it.
